# ADR-014: The learning loop needs a training corpus with shared shapes, and an identity that lets evidence accumulate

**Status:** Accepted · **Date:** 2026-09-01

## Context

The self-learning claim has never been measured. Every attempt reported "no
measured improvement", and each time the reason turned out to be mechanical
rather than empirical:

1. `swarmd eval` built both arms without a library, so they were the same code
   (found 2026-08-29, fixed in the CLI).
2. `_eval_runner` in the control plane did the same thing for four more days,
   so every eval started from the dashboard was a null-result generator
   (found 2026-09-01, fixed).
3. The session trained on the tasks the eval measured, so any improvement it
   did show would have been memorisation (found 2026-09-01, fixed).

With all three fixed, a clean experiment ran: ten tasks on the `public` set,
live providers, 458 seconds. It produced **22 skills, 0 promotable, 0
approved** — and therefore still no measurement.

This ADR is about why, and it is not another bug.

## The diagnosis

A skill becomes reviewable when it is `promotable`: verified on
`MIN_DISTINCT_TASKS = 2` distinct task shapes. That bar is the thing that makes
"does this approach transfer?" a question with an answer — one task's evidence,
drawn twice, says nothing about a second task.

Two independent preconditions have to hold for any skill to clear it. Neither
held.

**The corpus had no shared structure.** Promotion asks for one approach that
worked on two *different* task shapes. The suite's twelve tasks have twelve
disjoint output shapes: a median repair, a colour-ordering puzzle, a pagination
strategy. No approach distilled from one of them is ever proposed by another,
so the bar is unreachable at any sample size. Measured: 22 skills across 5
training shapes, every one carrying exactly one shape.

This reframes the "50–200 tasks" item that has sat on the list for days as a
statistical argument. It is not statistical. It is structural: a thousand
mutually-unrelated tasks would promote exactly as many skills as twelve, which
is none. What the corpus needs is **families** — several tasks that call for the
same kind of work and the same output shape — and volume is what makes the
resulting rate meaningful once the loop turns at all.

**And identity fragments on wording.** `make_skill_id` hashes the instruction
text, and the instruction is written by a model. The same approach distilled
from two runs comes back phrased differently every time, so it mints a second
record starting again from one shape. This was measured too, and it is why the
first attempt at a fix was wrong: grouping the 22 records by their abstracted
name and pattern still gave zero approaches with two shapes, so merging was
reverted as fixing nothing.

That measurement was taken on a corpus where no two tasks shared an approach at
all. It showed merging is **insufficient**, not that it is unnecessary. On a
corpus with families the fragmentation becomes load-bearing: two tasks propose
the same approach, phrase it differently, and the evidence lands in two records
of one shape each instead of one record with two.

**Both preconditions are required. Neither alone closes the loop.**

## Options considered

**Lower the bar to one task shape.** Rejected. `MIN_DISTINCT_TASKS = 1` means
"this worked once" is enough to offer a reviewer an approach and to inject it
into future runs. That is not a transfer claim, and the retrieval path would
fill with one-off advice — which is the failure the bar was added to prevent,
and the reason the library once held entries anchored to plan node names.

**Bypass the bar with `approve(..., force=True)`.** Rejected as the primary
answer, kept as a labelled fallback. It produces a number today, and the number
measures whether *retrieval of unvalidated advice* helps. That is a real
question and a different one from the claim being made, and the bypass is
recorded on each record precisely so a result built on it cannot be quoted as
transfer.

**Coarsen what counts as a task shape.** Rejected. It makes the bar easier to
clear by making the question weaker: two shapes that are "the same" only because
the fingerprint stopped distinguishing them are one shape, and the bar would be
satisfied by the same task twice.

**Similarity threshold over skill text.** Rejected. A tuned float deciding
whether two approaches are the same makes library membership depend on a
threshold nobody can justify, and it is exactly the probabilistic decision this
project keeps out of the deterministic path.

## Decision

**1. A `train` arm, structurally separate from every evaluated set.**

Fifteen tasks in five families of three. Each family shares an output shape, so
an approach distilled from one member can be proposed by another and accrue its
second piece of evidence honestly. Each family is aligned with a *kind* of work
the `custom` arm also needs — diagnosis and minimal fix, checkability verdict,
constrained enumeration, rate-limited planning, name normalisation — so that
what transfers, if anything transfers, is the approach and not the task.

The training set is **not evaluable**, and that is enforced rather than
observed: `SessionRequest.arms` accepts `train`, `EvalRequest.arms` does not.
A measurement over the tasks a library was built from is contamination, and the
way to prevent it is to make it unexpressible.

`both` continues to mean `public + custom`. A training set that silently joined
the evaluated suite would be the contamination this decision exists to stop.

**2. Evidence accrues on the approach, not on its wording.**

`propose()` keys evidence on a content hash of the *abstracted name and task
pattern* — the same abstraction the retrieval index already uses, which already
holds no literals. `skill_id` still addresses the instruction content, so a
stored record still verifies against its own hash and the advice is still
exactly what was proposed; what changes is that a re-proposal of the same
approach lands on the existing record instead of beside it.

Retired records are excluded from the match: reviving a pruned approach through
a re-proposal would undo a decision someone made.

## Consequences

**The loop can turn.** Whether it actually improves anything is now an empirical
question with an answer, which it has not been at any point in this project's
history.

**The first instruction wins.** When two wordings merge, the stored advice is
the one proposed first; the second is discarded rather than blended. Blending
model text is how a library fills with advice nobody wrote. A visibly worse
first wording is a pruning problem, and pruning already exists.

**Two different approaches to the same kind of step will merge.** The name and
pattern are what the library already retrieves on, so two records that abstract
identically were already competing for the same retrieval slot. The human gate
and success-rate pruning are what decide between them, and both still apply.

**A training corpus is a maintained artifact.** Fifteen hand-written tasks are
a thing that can go stale, and a family whose members stop sharing an output
shape silently stops producing evidence. The session report's promotable count
is the signal for that, and it is now a number worth watching rather than a
constant zero.

**The result may still be "no measured improvement".** That is now a permitted
outcome rather than a foregone one — the difference this ADR is for.
