# ADR-011: Provider quota is a cluster resource, coordinated in Redis

**Status:** Accepted · **Date:** 2026-08-28

## Context
Provider rate limits are enforced **per account**, not per process. A token
bucket living in one Python process is correct exactly while one process holds
the credential.

The moment the system runs on Kubernetes with more than one replica, that
assumption silently inverts. Three pods each correctly limiting themselves to
45 RPM present 135 RPM to the account. The provider throttles all three. Each
pod's backoff logic then interprets a self-inflicted 429 as evidence about the
*provider*, tightens against a problem it caused, and the pods oscillate
together because they are all reacting to the same signal at the same time.

This is a class of bug that does not appear in development, does not appear in
a single-pod deployment, and appears immediately on the first horizontal scale
— which is to say, in production, under load, during a demo.

## Decision
Quota is an interface with two implementations, selected by configuration.

- `InProcessQuota` — token bucket in memory. The default. Correct iff exactly
  one process holds the credential, which is the single-node case, and paying
  for a network round trip to coordinate with yourself would be absurd.
- `RedisQuota` — the same bucket, evaluated inside Redis as a single Lua script.
  Correct for any number of pods. Required by the Kubernetes deployment, which
  always sets `SWARMD_REDIS_URL`.

Three details are load-bearing rather than incidental:

**The bucket refills continuously.** A fixed window permits spending the whole
minute's allowance in its first second, which reads to the provider as a burst
and earns a 429 despite a legal average. Continuous refill is what "30 requests
per minute" means to the thing enforcing it.

**Redis evaluates the whole decision.** Check-then-decrement across two round
trips is a race, and with hundreds of agents contending it is not a rare one.
The script makes check and spend atomic.

**Redis supplies the clock.** Pod clocks drift. A bucket refilled against a fast
clock hands out permits that do not exist yet.

**Keyed per credential, not per provider.** Two Groq keys are two accounts and
genuinely two quotas; keying on provider name alone would throttle them as one
and discard half the capacity that was paid for (in signups, if not money).

## Consequences
- Redis becomes a production dependency, but only in the multi-replica
  deployment. Single-node runs and CI keep zero new infrastructure.
- A Redis outage degrades rather than breaks: pods fall back to local buckets at
  25% of the real rate. Fail-open would produce exactly the stampede this ADR
  exists to prevent; fail-fully-closed would turn a Redis blip into total
  outage of a system whose entire premise is graceful degradation. 25% is sized
  so that a plausible number of blind pods still sums to under the account
  limit.
- Quota state is deliberately ephemeral (5-minute TTL). Losing it costs one
  window of over-permissiveness, whereas persisting it would mean a stale
  bucket from a dead deployment throttling a live one.

## Follow-ups
**Why not just run one replica and avoid the problem?** That caps throughput at
one pod, makes deploys an outage, and gives up the horizontal scaling story
entirely. It also does not actually avoid the problem — a second replica appears
the moment anyone runs a rolling update, so the bug exists in the deploy path
even at replicas=1.

**Why Redis rather than a dedicated quota service?** A quota service is the
right answer at an organisation with many teams sharing provider accounts, and
it is the wrong answer here: it is another deployment, another failure domain,
and another on-call surface to serve one bucket per credential. The interface
means swapping it later is a class, not a refactor.

**How is this tested without a Redis?** The bucket mathematics are tested
directly against a controlled clock. The degradation path is tested with an
unreachable Redis, which is the failure mode that actually matters. The Lua
script's atomicity is asserted structurally — the read and write are in one
script — since a race that only appears under real contention cannot be proven
by a unit test either way.

**What if a provider meters per key rather than per account?** Then our
per-credential keying is already correct and the empirical limit discovery in
ADR-008 finds the real number. The pool never trusts the published figure.
