# ADR-013: Single-tenant operator-run service — no user auth, by decision

**Status:** Accepted · **Date:** 2026-08-28

## Context
swarmd is not a multi-tenant SaaS. One operator starts the service, submits
runs, reviews the human-gated queues, and stops it. There is no second user, no
tenant boundary to enforce, and no per-user data to separate.

The tempting shortcut is to say "it's just a demo, auth doesn't matter." That
framing is how a system ends up with no threat model, no retention policy, and
an API that turns out to have been reachable from the internet for a month. The
opposite over-correction — building OIDC, users, roles, sessions, and a consent
screen — is constructing a login for a population of one, and every one of those
components is a thing to maintain, patch, and get wrong.

So the question is not "auth or no auth". It is: **what is the actual threat, and
what is the smallest set of controls that addresses it honestly?**

## Threat model
Who realistically reaches this service, in descending order of likelihood:

1. **Nothing.** Most of the time it is off. Availability is not a goal.
2. **The operator**, from a laptop or a private network.
3. **Anything else that can reach the port**, if it is ever exposed by accident —
   a misconfigured Ingress, a `--host 0.0.0.0` in a shell, a LoadBalancer
   created without thinking.

What an unauthenticated caller could do with the run API is the part that
matters, and it is not nothing: start runs that consume a shared and strictly
limited provider quota, read every prompt and artifact of runs in flight, and
record human approval decisions that the audit trail would then attribute to a
person. The last one is the worst — it corrupts evidence rather than resources.

## Decision
No user accounts, no roles, no sessions. Instead:

**A single shared operator token** (`SWARMD_API_TOKEN`) gating every mutating
endpoint and the event stream. This is authentication of the *operator*, not of
*users* — there is one principal and one credential.

**The service refuses to start** bound to a non-loopback interface without a
token. Not a warning at first request: fatal at startup, before exposure. The
value of the check is entirely in when it happens.

**Read/write split.** `/healthz`, `/readyz` and `/metrics` stay open so
Kubernetes and Prometheus can scrape without holding a credential that could
also start a run. Reads of run history stay open behind the network controls.
Anything that spends money or records a human decision requires the token.

**Rate limiting as a quota defence, not a DoS defence.** The scarce resource is
~45 provider requests per minute shared by the whole system; a loop in a script
can burn a day's free tier before anyone looks.

**Network controls are primary.** The token is the layer beneath. The backend is
never given a public route: the Ingress exposes the dashboard behind an IP
allowlist, `/api` is reachable only from the frontend and the ingress
controller, and the NetworkPolicy denies everything else.

## Consequences
- No login screen to build, no session store, no password reset, no account
  recovery — none of which would serve anyone.
- One credential means no revocation granularity: rotating it logs out
  everything. Acceptable at one principal; the first thing that breaks if a
  second operator ever appears, and that is the point at which real identity
  becomes worth building.
- The audit trail records `actor` as a supplied string rather than a verified
  identity. Honest within the posture — the trail proves *what* was decided and
  *when*, not *who*, and the docs say so rather than implying more.
- Anyone holding the token can do anything. The token is stored in Secrets
  Manager and synced by External Secrets like any other credential.

## Follow-ups
**Isn't "no auth" just a security hole with a paragraph attached?** The
distinction is whether the controls match the threat. There is no unauthenticated
path to start a run, read a stream, or record a decision; the service refuses to
run exposed without a credential; and the network layer means the port is not
reachable in the first place. What is absent is *multi-user identity*, and there
are no multiple users.

**What changes on the day a second person needs access?** OIDC via an
authenticating proxy at the Ingress, with the app unchanged — it already treats
the request as pre-authenticated. That is a deployment change, not a rewrite,
which is the reason for putting the boundary at the edge rather than in the app.

**Why is the metrics endpoint open?** Because the alternative is giving the
Prometheus scraper a token that can also start runs, which is a wider grant than
scraping needs. Metrics carry no per-task identifiers by policy, so the
endpoint's content is aggregate counts.

**What if the token leaks?** Rotate it in Secrets Manager and restart the
deployment — `envFrom` is fixed at container start, so a rotation alone does not
take effect, which is documented in the runbook rather than discovered during an
incident.

**Why not just leave it open and rely on the network?** Because a single
misconfigured Ingress annotation would then be the whole failure. Defence in
depth costs one header here.

## Addendum, 2026-08-29: the token is out of MVP scope

**Status of the decision above: unchanged. Status of the token: not shipped in
the MVP.**

The section immediately above asks "why not just leave it open and rely on the
network?" and answers that defence in depth costs one header. That answer still
stands on the merits. The MVP is shipping without the token anyway, and the
honest reason is scope rather than a change of mind about the threat.

What that means concretely:

- **The network control is now the only control**, not the primary one. Its
  failure mode is no longer "degraded to one layer"; it is "open". The
  NetworkPolicy in `deploy/k8s/base/rbac-and-config.yaml` admits port 8000 from
  the dashboard pod and the ingress controller and denies everything else, and
  `tests/test_deploy_guards.py::test_open_mode_is_backed_by_a_network_policy`
  fails the build if that policy is deleted while open mode is declared. The
  guard exists because the reasoning is now load-bearing.

- **Open is a decision, not a default.** The startup refusal is unchanged: bind
  a non-loopback interface with no token and the process exits. Running open
  requires `SWARMD_ALLOW_OPEN=1` (or `--allow-open`), set in the ConfigMap where
  a reviewer sees it in a diff. `SWARMD_ALLOW_OPEN=false` does not count as
  consent — presence is not truth.

- **Every start says what is exposed.** `serve` prints the exposure line to
  stdout rather than only logging it, because a warning that reaches the log
  during startup is a warning nobody reads.

- **Nothing was removed.** The middleware, the constant-time comparison, the
  read/write split and the rate limiter are all still there and still tested.
  Setting `SWARMD_API_TOKEN` turns auth on with no code change. This is a
  configuration decision that can be reversed in one line, which is the only
  reason it is an acceptable thing to defer.

**What this costs, stated plainly.** Anything that can route to port 8000 can
submit runs, and runs spend real provider quota. In the deployed topology
nothing can, by policy. Outside it -- a laptop, a VM with a permissive security
group, a cluster whose CNI does not enforce NetworkPolicy -- there is no second
layer. The rate limiter bounds the damage per client; it does not prevent it.

**The trigger to revisit:** a second operator, any route that is not behind the
Ingress allowlist, or a CNI without NetworkPolicy enforcement. Any one of those
makes the token the cheapest remaining control.
