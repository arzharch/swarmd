# ADR-006: Mock provider is a test double only, never a demo path

**Status:** Accepted, AMENDED by [ADR-012](ADR-012.md) · **Date:** 2026-08-27 · **Amends:** ADR-004

> ADR-012 permits a simulated provider outside `tests/` for development without
> credentials, fenced by data taint rather than by code organisation. The ban on
> *reporting* from synthetic data is unchanged and is now enforced by a raise.

## Context
ADR-004 made the deterministic mock the *default* provider so demos ran offline with no
key. That was right when the product claim was orchestration correctness — a mock is a
perfectly good workload generator for proving checkpoint recovery.

It is wrong now. The v3 claims are about capability on unknown tasks, measured improvement,
and cost per solved task. Every one of those numbers is meaningless if the model behind it
is a schema-shaped stub. Worse, a live dashboard fed by mock output looks identical to one
fed by real output, so the mock stops being a convenience and becomes a way to accidentally
lie.

## Decision
The mock provider exists in `tests/` as a test double and nowhere else. Demo runs, the
frontend, and `swarmd eval` always hit real providers. CI enforces the boundary with an
import check that fails the build if a demo, example, or frontend path reaches the mock.

The one thing the mock keeps: the chaos integrity gate. Proving that output is
byte-identical under random kills requires a deterministic generator, and that test lives
in `tests/` where the mock is legitimate.

## Consequences
- Every demo needs network and at least one free-tier key. Documented in the README as a
  prerequisite rather than discovered at runtime.
- CI stays free and offline for unit tests; the eval smoke run is the only networked job.
- The frontend can never render data that did not come off a real run.
- Losing "offline-first" as a headline feature is accepted. It was protecting a claim we no
  longer make.

## Follow-ups
**Doesn't this make CI flaky?** Unit tests use the mock and stay hermetic. Only the eval
smoke job is networked, it is a separate job, and its failure is reported as a provider
outage rather than a code regression.

**Note added 2026-09-01, not a change of decision.** The networked eval job
described above was never built, and on reflection it should not be: this same
ADR is what makes `swarmd eval` refuse simulated data, and a credentialled job
in public CI would put provider keys in the one place this project has
otherwise kept them out of. The consequence line predicted a job that the
decision itself argues against. CI is hermetic throughout; what it asserts
about the eval is that the refusal fires. `docs/SPEC.md` Phase 11 carries the
same correction.

**What if every free tier is down during a demo?** The pool router falls through to paid
overflow within the $0.05 ceiling. If that is also exhausted, the run aborts with a report
saying so — which is honest, and is the same abort path the ceiling test exercises.

# ADR-007: The append-only ledger is the only source of any reported number

**Status:** Accepted · **Date:** 2026-08-27

## Context
"Our agents got 40% better" is the single most over-claimed sentence in this field. It is
usually computed from in-process counters, over runs with no control, on tasks the authors
chose after seeing the results.

The system being built here is *specifically* one that improves itself. That makes it
maximally exposed to the criticism, and no amount of prose disclaimer helps.

## Decision
Two structural commitments, enforced in code rather than asserted in docs.

1. **Ledger-only metrics.** Every LLM call, gate outcome, containment, and verified success
   writes an append-only row. Every number in every report is a query over those rows. No
   report may read an in-process counter. Cache hits still write rows, at zero cost, so
   "how much did the cache save" is a query rather than an estimate.

2. **No claim without a control.** `swarmd eval` refuses to emit an improvement figure
   unless a paired control run exists with identical tasks and seeds and skills disabled.
   Overlapping confidence intervals are reported as "no measured improvement" — that string,
   deliberately, so the failure mode is a visible non-result rather than a soft spin.

## Consequences
- Metrics cost a write per event. Accepted; the ledger is local and batched.
- Every run costs roughly double in eval mode, because the control arm is not optional.
  Accepted — half the compute buys the only thing that makes the other half meaningful.
- An agent cannot inflate its own scoreboard, because it does not hold the scoreboard.

## Follow-ups
**Why not just trust the counters and be careful?** Because the counters live in the same
process as agents that are selected on their reported success, and the economy pays on
verified success. Anything an agent can write, selection pressure will eventually teach it
to write dishonestly. Removing the capability is cheaper than policing it.

**Isn't the control arm just the same system with a flag off?** Yes, and that is the point.
The ablation isolates exactly one variable — whether retrieved skills are available —
against identical tasks, seeds, chaos schedule, and budget.

# ADR-008: Scale stance reversed — 1000+ agents, with the LLM as a rationed resource

**Status:** Accepted · **Date:** 2026-08-27 · **Supersedes:** ADR-001

## Context
ADR-001 capped the stance at 10–50 agents and explicitly disclaimed scale, on the reasoning
that big agent counts are easy to fake with sleep loops and distract from the real problems.

That reasoning still holds *for fan-out*. It does not hold for the v3 flagship, where
population size is load-bearing: population search, market selection, and multi-proposal
criterion synthesis all become theatre at N=20. You cannot run a market with twenty
participants; that is a meeting.

Measured constraint (August 2026): pooled free-tier throughput across Groq, Cerebras,
Google AI Studio, Mistral, and OpenRouter is roughly 86,000 TPM, about 34 LLM calls per
minute. At the $0.05 ceiling, paid overflow adds roughly 180 calls. A thousand agents each
calling a model per step is not budget-constrained, it is physically impossible.

## Decision
Target 1000+ concurrent agents, and define the claim precisely: **most agents are not
talking to a model at any instant.** Skill retrieval, sandboxed execution, verification,
ledger accounting, and red-team monitoring are all pure computation. The LLM is the scarce
resource and the runtime's job is rationing it — cache first, batch where possible, route
across providers, and refuse when the ceiling is near.

Every published agent-count figure carries cost per solved task next to it.

## Consequences
- The interesting engineering moves from "spawn many agents" to "make agent-steps cheap",
  which is the more defensible and more transferable problem.
- The semantic cache and token-budget code written in Phase 4 become load-bearing rather
  than decorative — a run's feasibility depends on hit rate.
- Runs are minutes-to-an-hour, not seconds, because throughput is capped. Accepted, and it
  is why the live dashboard exists.
- ADR-001's anti-fake-parallelism concern is answered by publishing cost alongside count,
  not by capping the count.

## Follow-ups
**Isn't "1000 agents, most idle" just a smaller system with extra bookkeeping?** No —
population selection needs the whole population to *exist and hold state* (budget, skill,
lineage), not to be mid-call. Idle-but-alive is the normal condition of a market
participant.

**What happens when the pool is saturated?** Agents block on the scheduler's bounded queue,
which is the backpressure path from Phase 1. The run degrades to fewer effective agents and
reports that, rather than dropping work.

**Why not pay for throughput?** Nothing stops it, and the router already supports paid
providers. The $0.05 ceiling is a self-imposed constraint that forces the rationing
engineering to be real. Raising it is a config change, not a redesign.
