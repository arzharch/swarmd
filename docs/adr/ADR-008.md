# ADR-008: Rate limits are discovered from observed 429s, not read from docs

**Status:** Accepted · **Date:** 2026-08-26 · **Supersedes:** the single-provider client in [ADR-001](ADR-001.md)

## Context

This system runs on pooled free tiers. Free-tier limits are the binding
constraint on everything — how many agents can run, how long a run takes,
whether the capacity plan in [CAPACITY.md](../CAPACITY.md) holds — and they are
the least reliable numbers available:

- Published limits are frequently stale, and the documented figure is often
  not the enforced one.
- Limits differ per *credential*, not per provider. Three Google keys are three
  buckets, and a client that models one bucket per provider will either
  under-use two of them or 429 constantly on one.
- Providers apply undocumented per-model and burst limits underneath the
  headline number.
- They change without notice, and nothing announces it.

A constant compiled from documentation is a claim about someone else's
infrastructure that nobody re-checks.

## Decision

**Treat the published limit as a starting hypothesis and the observed 429 as
the fact.**

- `ProviderPool` holds credentials, not providers. Quota is tracked per
  credential (`LimitState`), because that is the unit the provider enforces.
- A 429 narrows the credential's effective rate immediately; a sustained run of
  successes widens it back, decaying toward the configured ceiling.
- Discovery is lazy — the bucket is initialised from the first observed
  behaviour rather than in `__init__` — so a key that is never used costs
  nothing and a key whose limit changed corrects itself on first contact.
- `swarmd providers probe` (and `POST /api/providers/probe`) reports what the
  pool currently believes about each credential, so the operator sees observed
  reality rather than the config file.
- Tier ordering routes to free credentials first and falls back to the cheapest
  paid model with adequate context, keeping a run inside the $0.05 ceiling.
- Across replicas the bucket is shared through Redis; see
  [ADR-011](ADR-011.md).

## Consequences

- The system adapts to a provider silently halving a limit, with no deploy.
- Capacity figures are measured rather than asserted, which is why
  CAPACITY.md's numbers can be checked against a run.
- Cold start is slightly conservative: the first minute of a run discovers
  headroom rather than assuming it.
- Backoff state is per-process unless Redis is configured, so a single pod's
  discovery does not automatically inform its neighbours.
- The decay path needed a `>` changed to `>=`: on Windows the monotonic clock's
  ~15ms granularity made a 429-to-success delta of exactly 0.0 fall through the
  comparison, which silently disabled the widening half of the loop. A limiter
  that only ever narrows looks like a working limiter for as long as anyone
  watches it.

## Alternatives considered

**Configured constants per provider.** Simple, and wrong the first time a
provider changes anything. It also cannot express per-credential limits, which
is the whole reason for pooling keys.

**One shared bucket per provider.** Under-uses multiple credentials by exactly
the factor they were added for.

**No limiting; retry on 429.** Retries are cheap for the client and expensive
for the run: a swarm that discovers its limit by hitting it repeatedly spends
its wall-clock budget in backoff.
