# ADR-012: Simulated provider, fenced by data taint rather than configuration

**Status:** Accepted · **Date:** 2026-08-28 · **Amends:** [ADR-006](ADR-006.md)

## Context
ADR-006 confined synthetic responses to `tests/` and banned them from every
demo, frontend, and eval path. The reasoning was sound and still is: a
dashboard fed by a stub is pixel-identical to one fed by a real model, so the
mock stops being a convenience and becomes a way to accidentally lie.

That decision has a practical cost which has now arrived. Phases 6 through 10
build criterion synthesis, plan synthesis, the worker pool, the red-team organ,
the skill library, and the frontend. All of that needs a provider to develop
against, and provider credentials do not exist yet. Under ADR-006 as written,
development is blocked on a key.

The tempting resolution — "just allow the mock during development" — reproduces
exactly the failure ADR-006 exists to prevent. A configuration flag is a weak
fence: it gets set three shells ago and forgotten, `.env` files get copied
between machines, and a stale export survives a terminal session longer than
anyone's memory of setting it.

## Decision
Add a `SimulatedProvider` in `src/`, and fence it on the **data** rather than on
the configuration.

Every response it produces writes a ledger row carrying `simulated=True`. That
flag propagates:

1. **Row → report.** `CostAccount.report()` sets `simulated: true` if *any* row
   is tainted. A run that mixed real and synthetic calls is not a real run —
   it is a run whose numbers mean nothing in particular, and saying so is the
   only honest option.
2. **Report → publication.** `refuse_simulated(report, context=...)` raises. Any
   code path that publishes a number — `swarmd eval`, benchmark generation, an
   improvement claim — calls it first.
3. **Report → UI.** The dashboard reads the same flag and renders a permanent
   banner.
4. **Config → CI.** A test fails the build if the enabling variable appears
   truthy in any deploy manifest.

Two supporting choices:

**Construction requires the environment variable**, not a constructor argument,
so enabling it is visible in `env`, in a pod spec, and in a diff — somewhere a
reviewer can see it — rather than buried in a call site. It is never a fallback
for a missing key: a run with no providers fails loudly instead.

**Simulation is exclusive, not additive.** When enabled, the pool contains only
the simulated provider. A pool mixing real and synthetic providers produces a
run that is part measured and part invented with no way to say which half a
figure came from.

## Consequences
- Development proceeds without credentials, which unblocks Phases 6–10 and the
  entire frontend track.
- The guarantee is *stronger* than ADR-006's, not weaker. ADR-006 relied on the
  mock being absent from certain code paths — a property that holds until
  someone adds an import. Taint holds regardless of code path, configuration
  mistake, stale environment, or a ledger file copied from a development
  session by mistake.
- Every report gains a `simulated` field. Consumers must handle it; that is the
  point.
- Default latency is non-zero (50ms) and a seeded failure rate is available.
  A fake provider that answers instantly and never fails hides every
  concurrency, backpressure, and error-path bug the system exists to handle,
  which is how software passes all its local tests and falls over on first
  contact with a real API.

## Follow-ups
**Isn't this just re-permitting what ADR-006 banned?** ADR-006 banned synthetic
data being *indistinguishable downstream*. It achieved that by keeping the mock
out of certain paths, which is a property of code organisation and therefore
one refactor away from being false. This achieves it by marking the data, which
survives refactors. The ban on *reporting* from synthetic data is not relaxed
at all — it is now enforced by a raise rather than by convention.

**Why not delete it once real keys arrive?** Because CI will always want a
network-free path, the chaos integrity gate needs a deterministic generator,
and the frontend needs something to render in a demo with no credentials
configured. What matters is that none of those can be mistaken for a real
result, and now none of them can.

**What stops someone removing the taint flag to make a report look real?** In
this repo, review and the tests that assert the flag propagates. In principle,
nothing — anyone with commit access can delete a control. The distinction worth
making is between an *accident* and a *decision*: this design makes presenting
synthetic data as real require a deliberate, visible code change rather than a
forgotten environment variable.

**Does the taint survive a process restart?** Yes. It is a column in the
append-only JSONL ledger, so a ledger file read back in a later process still
reports as simulated. That is specifically why the flag lives on the row rather
than in a run-level config object.
