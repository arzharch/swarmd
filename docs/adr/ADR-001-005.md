# ADR-001: Multi-agent orchestration stance (10–50 agents), not mega-swarm

**Status:** SUPERSEDED by [ADR-008](ADR-006.md) · **Date:** 2026-08-24

## Context
Original vision claimed 1,000+ concurrent agents. That number is achievable with trivial
sleep-loop agents but invites the (fair) criticism of fake parallelism, and it hides the
harder problems: stage coordination, quality gates, human approvals, partial-failure
recovery.

## Decision
Target 10–50 concurrent agents in dynamic per-stage pools. Concurrency is real and
benchmarked (parallel-vs-serial speedup), but the product claim is orchestration
quality: recovery from failed state, quality gates, durable HITL, traceability.

## Consequences
- Benchmarks emphasize speedup and integrity, not headcount.
- Kernel still supports high concurrency mechanically; we just don't sell it.

# ADR-002: Flagship application (LeadOps) lives outside the kernel

**Status:** Accepted (flagship changed to the generalist swarm in PRD v3; the kernel-purity rule this ADR establishes is unchanged and LeadOps remains as second-domain proof) · **Date:** 2026-08-24

## Context
A runtime without a real workload is a benchmark in search of a reason. But business
logic inside the kernel would make it a framework.

## Decision
`src/swarmd/` stays pure infrastructure. The LeadOps sales pipeline (INGEST → ENRICH →
DEDUPE → SCORE → DRAFT → QA → REVIEW) lives in `examples/leadops/` as a first-class,
production-shaped embedder — proving the kernel by using it the way a real user would.

## Consequences
- Every kernel feature must be exercised through LeadOps before release.
- LeadOps doubles as reference documentation for embedders.

# ADR-003: Outreach never auto-sends

**Status:** Accepted · **Date:** 2026-08-24

## Context
Automated outreach has real-world cost (spam, reputation, compliance). An agent runtime
that sends emails autonomously is a liability demo.

## Decision
The pipeline terminates at a durable REVIEW QUEUE state. Sends happen only after explicit
human approval via CLI/API, recorded in the audit trail. There is no auto-send mode.

## Consequences
- HITL durability becomes a core, demoable feature rather than an add-on.
- Email-provider integration is out of scope for v0.1; drafts + approval flow are the product.

# ADR-004: Offline-first with deterministic mock provider

**Status:** AMENDED by [ADR-006](ADR-006.md) · **Date:** 2026-08-24

## Context
LLM-dependent tests are flaky and paid; demos must not depend on free-tier availability.

## Decision
Default provider is a deterministic mock; open-data fixtures are committed. OpenRouter
adapter exists behind the same interface for real runs. CI never touches the network.

## Consequences
- Every gate is reproducible forever; chaos scenarios are controllable.
- Cache-hit benchmarks use mock embeddings with realistic similarity distributions.

# ADR-005: Supervisor self-correction with versioned prompt patches

**Status:** Accepted · **Date:** 2026-08-24

## Context
Fleet-level quality drift (systematic extraction errors) needs correction without
restarting runs. Naive hot-patching risks making things worse mid-run.

## Decision
Supervisor deep-agent reads QA failure taxonomy, proposes prompt patches, applies them
versioned to running workers, and tracks intervention outcomes. One-command rollback to
any prior patch version.

## Consequences
- Prompt changes become auditable artifacts, not chat history.
- Supervisor effectiveness is measurable (QA pass-rate delta post-patch).
