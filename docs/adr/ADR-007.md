# ADR-007: The ledger is the only source of reported numbers

**Status:** Accepted · **Date:** 2026-08-26

## Context

Every number this system publishes — cost, calls, cache hits, success rate,
learning curve — is a claim someone will check. The obvious implementation is a
counter incremented at the site that does the work: `self.calls += 1`,
`self.cost += price`.

Counters have three failure modes, and all three are silent:

- **They reset.** A process restart, a new pod, a re-run of a job: the counter
  starts at zero and reports a small number confidently.
- **They drift.** A code path that spends without incrementing is not a
  compile error, and there is no test that catches "this call site forgot".
  The system spends real money and reports less than it spent.
- **They cannot be audited.** A total is not evidence. Nobody can ask "which
  calls made up this figure?" of an integer.

The third one is what decides it. An agent economy pays on verified success and
clones profitable agents, so selection pressure searches for any gap between
what happened and what was reported. A number nobody can decompose is a number
nobody can dispute.

## Decision

**One append-only ledger per run. Every reported number is a sum over rows.**

- Every call, cache hit, and refusal appends a `LedgerRow`, fsynced on write.
- `CostAccount.total_cost()` sums the rows. There is no `self.total` field to
  drift from them.
- Prices are data (`PRICES`), not code. An unknown model raises `UnpricedModel`
  rather than defaulting to zero, because a silent zero is how a paid model
  gets billed as free.
- The cost ceiling is checked against the sum after each append, so a breach
  aborts with an itemised report rather than truncating.
- `swarmd ledger report|verify|inspect` reads the file. The dashboard's cost
  view and the CLI's summary answer the same query over the same rows.

Rows carry a `simulated` flag; see [ADR-012](ADR-012.md) for how that taint
propagates into every report derived from them.

## Consequences

- Reported cost cannot exceed or understate actual cost without the rows
  disagreeing, and the rows are on disk.
- Any figure can be decomposed: "which 41 calls made up this $0.031" is a
  filter, not an estimate.
- Restarts do not reset anything, because nothing is held in memory to reset.
- Summing on every read is O(rows). Runs are bounded by the ceiling long before
  that matters; a run large enough for it to matter would have aborted.
- New accounting must add a row kind rather than a counter. This is deliberate
  friction: it is exactly the moment someone would otherwise add a number with
  no evidence behind it.

## Alternatives considered

**Counters with periodic reconciliation.** Cheaper reads, and the
reconciliation job is one more thing that can be broken for a week without
anyone noticing. The failure mode is a system that looks correct.

**Provider-reported usage as the source of truth.** Right for billing,
useless for a ceiling: it arrives after the money is spent, per billing period,
not per run.

**Metrics as the source of truth.** Prometheus counters reset on restart and
are sampled, not exact. They are the right place to *observe* the ledger and
the wrong place to *be* it — which is why `metrics.py` reads from the ledger
rather than the reverse.
